# 产品愿景（草案 v0.2）

> 本文档定义 Verkee Verify × Verkee Guard 两个项目的统一北极星与商业路径。
> 状态：草案，待作者审定后同步至两个仓库；重大方向变更必须更新本文档。
> v0.2（2026-07-26）：验真层改为「场景 × 用户困惑」框架，弃用归因断言式表述；「降质」统一更正为「降智」。

## 一句话愿景

**让每一个人都能信任替自己干活的 AI。**

AI 时代的信任基础设施：验真其身份，约束其行为，留存其证据。

## 问题：AI 成了员工，却没有"入职管理"

AI 正在从聊天工具变成替你干活的员工：改你的代码、花你的 API 额度、读写你的文件、调用你的凭据。但对照真人员工的入职管理，今天的 AI agent：

- **没有背调** —— 你付费买的是 GPT/Claude，中转站给你掉包、降智你无从知晓（Verkee Verify 的靶心）
- **没有权限边界** —— 一次同意变成永久通行，任务 A 的授权被挪给任务 B（Verkee Guard 的靶心）
- **出事没有证据** —— 会话日志说不清谁授权了什么、哪一步开始越界（共享审计层的靶心）

现有 AI 安全产品全部卖给"部署 agent 的大企业 IT 部门"，**agent 的使用者一侧是空的**。

## 产品栈：AI 信任栈（AI Trust Stack）

| 层 | 项目 | 回答的问题 | 现状 |
| --- | --- | --- | --- |
| **验真** | Verkee Verify | Cursor Auto 用了什么模型？中转/plan 有没有被降智？ | 渠道验真/透明代理/巡检周报，已可用 |
| **管控** | Verkee Guard | Agent 干的是不是那件事？ | M1 审计 / M2 实时 hook / M3 意图锁定，已完成 |
| **证据** | 共享审计层（规划中） | 出了事拿什么说清楚？ | 防篡改审计链，两项目格式互通 |

验真层的能力是同一块：看清"实际用了什么模型、质量有没有变化"。但**同一个能力，在不同场景下用户的困惑不一样**——产品要回答用户的原问题，而不是替用户下归因结论（场景均来自真实用户群观察）：

- **Cursor 用户：好奇"开了 Auto 以后，各种任务到底用了什么模型"** —— 产品内置模型路由对用户不透明，用户要的是知情权：每个任务实际跑了哪个模型，本地解析遥测即一清二楚
- **中转 API / 厂商 plan 用户：好奇"执行各类任务有没有被降智"** —— 花出去的钱值不值：指纹 + 质量题 + 反侦测探针，偷换模型、悄悄降智可测可查
- **舆情实证**：用户群里每隔几天就有人问"XX 模型是不是又被降智了" —— 这类问题没有工具只能吵架，Verkee Verify 给出可复现的判定方法

边界（现阶段的纪律）：回答"用了什么、有没有降智"，**不做"是模型的锅还是产品的锅"的归因断言**——归因需要更厚的证据积累，过早下结论反而损害可信度。

单独看都是小工具，合起来回答一个完整问题：**你凭什么信任 AI？**

## 客群：没有安全部门的 AI 重度用户

不按科班/非科班切分，按"有没有安全部门兜底"切分：

- 独立开发者、自由职业者（agent 是生产资料，出事就是真金白银）
- 2–10 人小团队（无专职安全，老板担心 agent 泄密）
- 用 AI 做副业 / 一人公司的知识工作者（正在爆发增长）

他们的共同点：让 agent 深度参与生产，却没有企业 IT 部门替自己兜底，只能自己当自己的安全官——而市场上没有为他们做的工具。

## 产品哲学（不可妥协的四条）

1. **安静精准（火绒式告警纪律）** —— 宁漏勿扰；告警服从率 ≈ 告警准确率，弹窗是会贬值的货币；绝不做 360 式弹窗轰炸
2. **本地优先** —— 正文不出本机，密钥 token 永不入库
3. **开源可信** —— 安全产品的信任来自代码可审计，不来自厂商承诺
4. **证据至上** —— 不渲染恐慌，只呈现可追溯的事实

## 商业路径（三层，按序推进）

1. **工具层（现在–1 年）：攒资产，不设付费墙**
   开源免费，目标是装机量、规则库社区、品类定义权（"agent 行为管控 = 我们"）。
   攒下的资产：用户、行为风险数据、社区规则库、口碑。
2. **小团队治理层（1–3 年）：开始收费**
   团队版：老板一个面板看清团队所有 agent 在干什么、统一下发策略、出事导出审计证据链。
   自下而上 PLG（参照 1Password/Snyk 早期），从第一层用户里自然长出，不打企业正面战。
3. **信任标准层（3–5 年）：想象力层**
   agent 替人花钱/签合同/操作生产系统后，AI 责任险与行为合规需要定价数据与定责证据标准。
   前两层攒的数据与审计标准即入场券。

## 不做清单（明确边界）

- 不做沙箱（Anthropic srt / Codex 已占，且是互补层：srt 圈地 + 我们站岗）
- 不做 MCP gateway 主叙事（IBM/Runlayer 企业混战）
- 不做 LLM 内容护栏（管"说什么"的赛道，我们管"做什么"）
- 不做企业端点管控正面战场（Backslash/微软 AGT/并购后的 PANW，是资本和渠道战）
- 个人版安全功能永不收费（安全是底盘；付费点只在效率与团队管理）

## 架构统一方向：Verkee Guard 向 Verkee Verify 靠拢

两个项目未来是一套架构，近期对齐项：

- **证据格式互通**：Verkee Guard 审计日志引入防篡改 hash chain，格式与 Verkee Verify "可追溯证据"对齐，未来可互相背书
- **告警通道复用**：Verkee Guard 复用 Verkee Verify 的飞书/钉钉 webhook 报警机制（团队版集中告警的基础）
- **存储对齐**：Verkee Guard 审计层按 ARCHITECTURE.md 既定方向引入 SQLite 索引（复用 Verkee Verify 的 aiosqlite 经验）
- **CLI 体验同族**：config init/set/list、report --period weekly、monitor 等命令族保持一致
- **远期**：统一品牌下的单一家目录与 CLI 入口（验真 + 守护子命令）

## 推广节奏

- **先锋是 Verkee Verify**：先在朋友圈/社群推 Verkee Verify 试用（AI 消费验真离钱近、痛点直观），攒第一批种子用户与口碑
- **Verkee Guard 跟进**：借 Verkee Verify 的用户反馈打磨 M3.5 告警纪律，M4 规则库引入社区共建
- 更名与新品牌：尽量在首轮公开推广前定稿，避免种子用户记住旧名

## 品牌

主品牌定名：**守真 / Verkee**（中文主名守真，英文主名 Verkee；命名渊源：守真 ↔ 浙大"求是"校训同属求真传统）。
定名依据：旧名 VERKEEP 因中国商标第9类 KEEP 注册与 EVERKEEP 家族冲突弃用，VERKEE 三源检索干净且域名可注册。
两个产品作为品牌家族挂载：**守真·验（Verkee Verify，原 VerAI）**、**守真·卫（Verkee Guard，原 AgentGuard）**。
远期合并为一套架构后品牌结构可能再收敛，本文档随之更新。

## 北极星指标

- 装机/活跃（两项目合计）
- 规则库社区贡献数（Verkee Guard M4 后）
- 告警值得率：转人工的告警中被用户认为值得的比例 ≥ 90%（火绒式纪律的量化北极星）
- 种子用户 NPS / 自发推荐（首轮推广期）
